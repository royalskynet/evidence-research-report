# 證據政策

需要判斷來源品質、處理爭議、監管或法律主張時，完整讀取本檔。

## 不可妥協規則

1. 搜尋結果、摘要、AI 摘要與標題只能用來發現來源，不能支撐正文主張。
2. 引用前必須讀取實際頁面、文件或資料集，並確認它直接支持主張的主體、範圍、時間與限定語。
3. 無法讀取或無法支持的內容不進正文；重要缺口放入「資料缺口」。
4. 不得把合理推測寫成事實。必要分析標為 `[推論]`，並緊鄰列出其事實依據。
5. 來源數由問題覆蓋決定，不設固定最低或最高數量。

## 依主張判斷來源等級

| 等級 | 適用來源 | 可以證明 | 不能單獨證明 |
|---|---|---|---|
| S0 | 法律原文、監管機關、法院、政府登記、正式申報、原始資料 | 法律要求、登記或裁判內容、申報事實 | 未被文件直接處理的延伸結論 |
| S1 | 公司官網、產品／API 文件、公告、狀態頁、安全文件 | 公司自述、功能規格、公告內容 | 實際成效、業界領先、客戶滿意或爭議清白 |
| S2 | 合作方公告、具編採責任的獨立媒體、正式採購文件 | 獨立報導、合作方立場、已公布採用 | 未披露的商業條款或技術成效 |
| S3 | 有方法說明的研究、學術或產業分析 | 方法範圍內的分析結果 | 超出樣本、日期或方法的普遍結論 |
| S4 | 社群、論壇、聚合頁、搜尋摘要 | 後續調查線索 | 任何核心結論 |

「官方優先」不是絕對排序。供應商官網適合證明其產品聲明；監管要求應以監管或法律原文為先；爭議與成效應找獨立或原始事件資料。

## 權威源直達表（S0 直接檢索）

盡調與監管／法律主張不靠搜尋引擎碰運氣；優先直達下列原始庫：

| 主題 | 直達源 | 用法 |
|---|---|---|
| 制裁／PEP | OpenSanctions（https://www.opensanctions.org/） | 網頁查詢免金鑰；yente API 可供程式化查詢 |
| 公司註冊（跨區） | OpenCorporates（https://opencorporates.com/） | 跨司法區的公司、董事與控股結構查詢 |
| 公司註冊（逐區） | 各主要司法區官方 registry | 依報告主體所在區，以「<司法區> company registry official」先定位官方網址，再直達原文 |
| 司法／監管 | 各司法區官方裁判與監管檢索入口 | 依領域以「<司法區> <監管機關> official decisions」先定位官方入口，再直達原文 |

> 直達只保證「找到原始庫」，不保證「引用即正確」：任何外部工具（含 yente）的回傳仍須以 WebFetch 讀取實際內容後才可引用。

## 主張處理

- **產品能力**：官方文件可寫「官方文件顯示／公司稱」。若要寫「能有效降低風險」，需要成效資料或獨立證據。
- **合作關係**：優先雙方公告；只有單方公告時寫明來源邊界，不擴大成仍持續合作。
- **法律／監管**：優先現行法規、主管機關及正式解釋；媒體只能補充背景。
- **爭議、訴訟、制裁**：區分指控、立案、裁判、和解與最終結果，保留日期及程序狀態。
- **不存在／未提供**：除非權威完整資料能證明，不寫「不存在」；改寫為「在本次已查閱的公開來源中未找到」。
- **時效性**：可能變動的功能、合作、牌照與政策必須附資料截至日期。

重大、具爭議或直接影響決策的主張，應取得兩個彼此獨立來源；但一份直接且權威的 S0 原始文件已完整證明時，不為湊數重複引用。

## 來源衝突

並列以下內容，不自行消除差異：

- 具體衝突事項；
- 來源 A／B 的說法、日期與等級；
- 哪個來源較能直接證明該主張及理由；
- 仍無法判斷的部分。

## 引用與定稿閘門

- 每個重要事實、數字、政策、合作、事件或評級後放 `[N]`。
- 同一 URL 固定使用同一編號；參考資料列出標題、發布者、日期（如有）、查閱日期、完整 URL。
- 會影響決策的關鍵來源連結易腐爛，引用時存檔：`https://web.archive.org/save/<原文URL>`（免金鑰），並在參考資料記錄存檔 URL；離線無法存檔時保留原文 URL 並標註未存檔。
- 定稿前逐一檢查正文所有重要主張與其引用是否語意相符；不是隨機抽樣。
- 執行 `scripts/validate_report.py <report.md>` 檢查編號、URL 與未解標記。腳本通過不代表語意已核實，語意核實仍須人工逐項完成。
- 不使用外部模型作為引用裁判，不讀 shell 啟動檔，不把報告內容或 API key 傳送給未獲批准的第三方。
