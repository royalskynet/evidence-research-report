# 深度研究模式

只有使用者明確要求「深度、詳盡、完整、窮盡式研究」，或標準模式發現跨司法管轄區／重大決策所需的明確證據缺口，且使用者同意升級時，才讀取並執行本檔。

## 啟動前

先交代：

- 決策問題與研究對象；
- 包含／排除範圍及資料截至時間；
- 預計搜尋方向、來源類型與交付結構；
- 預計最多 4–6 個搜尋批次、通常保留 12–25 個真正有用的來源；這是上限參考，不是配額；
- 是否需要子代理。只有存在互不依賴的研究軸線且平台支援時才使用，最多 3 個；不得為同一問題重複搜尋。

如果使用者已明確要求深度研究，可直接執行上述範圍；否則先取得升級同意。小型問題、高風險單點法規確認仍可用快速或標準模式，以權威來源品質而不是搜尋量保證可靠性。

## 執行

1. 建立研究問題清單與完成條件。
2. 先找 S0／S1 原始來源，再針對成效、爭議與反方證據找獨立來源。
3. 每輪只補具名缺口；合併可並行的搜尋，避免重複開頁。
4. 保留來源台帳與主張台帳為「同名 YAML sidecar」（如 `report.ledger.yaml`），供驗證器交叉檢查。格式：

```yaml
sources:
  - id: S1
    url: https://...
    grade: S0          # S0–S4
claims:
  - id: C1
    claim: <重要主張原文>
    source_id: S1
    ref: 1             # 對應正文 [1]
    status: supported  # supported | conflict | excluded
```

> 每個主張都須有 `source_id` 與 `ref`；`status: conflict` 的主張必須在正文「來源衝突」節並列雙方說法，不能自行消除差異。
5. 主張狀態變更（支持→衝突／排除）時同步更新 sidecar，保持與正文一致。
6. 連續兩次搜尋沒有新增重要證據時停止，不為「看起來完整」繼續擴張。

## 定稿閘門

- 逐項核對所有重要主張與引用；弱證據或未證實內容移至資料缺口，不留在正文。
- 對核心結論寫出最強反論；若反論成立，降低確定性或加入前提。
- 確認來源台帳、主張台帳（YAML sidecar）與正文一致。
- 執行確定性驗證器並附台帳：`scripts/validate_report.py --ledger report.ledger.yaml <report.md>`；修正所有錯誤後才交付。

除非使用者要求，不輸出內部搜尋紀錄與台帳；保留在工作資料中，管理層只收到精簡報告。
