# 开发日志 — 两轮验证模式

**日期**：2026-08-28
**范围**：`claude/competitive-research-report/`

## 问题

现有的 `evidence-research-report` 技能已经内置了一条很强的单页抓取韧性链（见 `references/retrieval-resilience.md`）：某个来源被拦截或返回空壳 SPA 时，会依次尝试 curl → 带密钥的抓取服务 → 镜像 → 存档 → 本地反爬渲染，只有链上所有环节都失败才放弃。这条链解决的是「如何拿到这一个页面」的问题。

但另一个独立的、偏合规调研场景的工作流中出现了一个不同的问题：第一轮调研跑完之后，那些始终没有来源的主张该怎么处理？逐条无限重试负担不起；但直接悄悄删除又会丢掉一些本身就有信息量的事实（例如「该指标未对外拆分披露」）。同时，最终报告也必须读起来像一篇完整的分析成果，而不是一份「尝试过什么、失败了什么」的过程记录。

## 做法

`claude/competitive-research-report/SKILL.md` 在一次正常调研流程之上加了第二个更小的循环：

1. **第一轮**跑常规的搜索 → 抓取 → 引用流程，产出初稿，同时生成一份内部使用（不进入报告）的缺口清单：每一条最终仍标 `[待核实]` / `[⚠️ 页面不可达]` / `[资料缺口]` 的主张，都按失败原因打标——页面存在但打不开（"打不开/渲染失败"），或者根本找不到来源（"查无来源"）。
2. **第二轮**按标签给每条缺口恰好一次补强机会：
   - 打不开/渲染失败的项目，批量走既有抓取韧性链已经有的本地反爬渲染环节，按批次处理而不是逐条重试；
   - 查无来源的项目，合并派给一次子代理调度，让它换一个角度（换语言、换措辞、换替代原始来源）再试一次。
   
   不论走哪条通道，规则都很严格：只试一次，不重试，也不在同一项目上换另一条通道再试。这样无论第一轮产出多少缺口，第二轮的规模都是可控的。
3. **整合**把两轮结果合成一份报告。补上来源的项目直接在原处改写，附上新的引用编号；仍未解决的项目保留原本的信心标注，留在主张本该出现的那句话或那个表格单元格里。这里刻意不设「资料缺口」或「未解决项目」专属章节——把它们另外汇总列出，会让报告读起来像调研过程的状态报告，而不是关于研究对象本身的报告。

## 为什么另开一个技能，而不是给 `evidence-research-report` 加一个模式开关

两个技能服务的报告形态不同：`evidence-research-report` 面向开放式尽职调查问题，走 S0-S4 证据分级与快速/标准/深度路由，通用性更强。`competitive-research-report` 则是围绕固定的同业对比输出（对比表 + 按固定维度展开的逐机构分析）设计的对标类报告，两轮加缺口台账的纪律正是在这种场景下才有意义——这类报告的读者需要一份完整的分析文件，而不是研究过程的记录。分开做技能可以避免把这种工作流形态硬塞进 `evidence-research-report` 的模式系统里。本地渲染环节是刻意复用而非重做——见 `claude/evidence-research-report/references/retrieval-resilience.md`。
