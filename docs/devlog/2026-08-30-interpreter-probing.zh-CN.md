# 开发日志 — 探测解释器，而不是信任 `PATH`

**日期**：2026-08-30
**范围**：`claude/evidence-research-report/scripts/`、`references/retrieval-resilience.md`

## 问题

抓取韧性链的最后一层是本地渲染，由 `scripts/setup_render.sh` 负责装配。有 `uv` 时脚本会建一个隔离的 venv，这条路没问题；没有 `uv` 时会退到第 21 行：

```sh
VENV_PY="$(command -v python3)"
```

然后往这个解释器的 user site-packages 里装包。这个兜底路径假定 `PATH` 上第一个 `python3` 是一个能用的解释器。在一台该假定不成立的机器上，故障表现得非常难读。

同一台机器上另一个工具报出来的可见错误是：

```
ModuleNotFoundError: No module named 'yaml'
```

而最自然的应对——把这个包装上——不但没用，而且根本不可能有用。出问题的是一个 Homebrew 构建的解释器，它的 `pyexpat` 扩展加载失败：

```
ImportError: dlopen(.../pyexpat.cpython-3xx-darwin.so): Symbol not found:
  _XML_SetAllocTrackerActivationThreshold
  Referenced from: .../pyexpat.cpython-3xx-darwin.so
  Expected in: /usr/lib/libexpat.1.dylib
```

该扩展编译时依赖的 `libexpat` 比运行时实际解析到的那个更新。于是 `import xml` 挂掉，`xmlrpc.client` 跟着挂掉，`pip` 自身也就起不来了。也就是说，这个解释器没法装上它自己报缺失的那个包。错误信息指向一个缺失的模块，真正的故障却是往下两层的动态链接不匹配，而这条路径上的每一条信息都在把人引向错误的方向。

## 为什么修环境是在赌

有三种看起来顺理成章的修法，没有一种是明确正确的：

- **重装 Python formula。** 如果重装拉到的是同一份预编译 bottle，那就是把同样的字节和同样的不匹配再装一遍。
- **重装或重新链接 expat。** 在这台机器上 expat 根本不是独立的 keg——该扩展按设计就是链接系统自带的库，没有什么可以重新链接。
- **升级到更新的 Python formula。** 这是唯一真有机会的一条，但它是一场赌博：只有当新 bottle 恰好是针对这台机器实际拥有的库版本构建的，它才有效，而这件事不试就无从判断。它还会重建所有依赖它的 venv，影响面因此扩散到无关的工具上。这台机器上两个不同的 Python 版本共用同一条 bottle 血统、且都受影响，所以「先升一个看看」连变量都隔离不干净。

目前的工作解释是操作系统版本错配——bottle 构建时预期的系统 `libexpat` 比该系统实际提供的更新。这个解释与观察到的一切都吻合，但它是从症状反推的推论，而不是对照构建元数据核实过的结论；下面的决策刻意不依赖它成立。

## 做法：能力探测

不去修环境，而是挑一个**可被证明能用**的解释器：

```sh
if ! python3 -c 'import yaml' >/dev/null 2>&1; then
  for candidate in /usr/bin/python3 /usr/local/bin/python3; do
    if [ -x "$candidate" ] && "$candidate" -c 'import yaml' >/dev/null 2>&1; then
      # 前置一个 shim 目录，里面放指向该候选者的 python3 软链
      break
    fi
  done
fi
```

有三个性质决定了这是对的形状：

- **它测的是能力，不是身份。** 版本号、安装路径、formula 名称，全都只是「这个解释器能不能做我要它做的事」的代理指标。探测直接问原问题，因此在没人通知我们的环境变动下依然成立。
- **它会自行失效。** 一旦默认解释器恢复正常，这段守卫的条件为假，兜底分支再也不会触发。没有需要记得清理的收尾步骤，也不会留下会腐烂的固定指向。
- **它不要求把根因搞懂。** 上面那段诊断在细节上可能是错的，而探测无论如何都是对的。

被否掉的替代方案是硬编码一个已知可用解释器的绝对路径。它把故障模式倒了过来：今天能用，将来在一台没有该路径、或该路径本身也坏了的机器上，它自己就变成了故障的**成因**。

## 这对本仓库意味着什么

`setup_render.sh` 的无-`uv` 兜底就是这件事会咬人的地方。它按 `PATH` 上的位置挑解释器，然后往里装包来改动它——既用了最不可靠的选择策略，又对选择结果做了最具侵入性的使用。可以考虑：

- 装包之前先探测选中的解释器，不可用就换下一个候选，而不是在装配进行到一半时失败
- 更强地优先走 `uv` 管理的 venv 路径，因为隔离的 venv 从根本上绕开了这整类问题——那台受影响机器上基于 venv 的工具毫发无伤，基于 `PATH` 的工具则全部中招
- 当脚本依赖解释器具备某项能力时，把这件事写成一次探测，而不是写成一句注释

更一般地说：一个指名某个包缺失的依赖错误，不一定真的和那个包有关。当安装这个包的动作以牵连到安装器自身的方式失败时，嫌疑对象是解释器，不是包索引。
